# AI 医院资源查询与便民就医助手

> 第三届 OPC 接单吧实战能力大赛 · **软件与智能体赛道**
> 赛题：AI 医院资源查询与便民就医助手 ｜ **演示范围：北京** ｜ 目标：一等奖

---

## 一、这是什么

一个**主动联网检索**的医院资源查询助手：用户用自然语言提问（地区 / 医院 / 科室 / 资源 / 医生 / 便民事项），系统**实时检索公开信息**，按**统一四段式框架**输出，并逐条给出**来源标题、链接、来源更新时间与本次查询时间**。

**它不做什么**（写死在代码里，不靠模型约束）：
- 不做疾病诊断、治疗方案、处方或用药指导；
- 不承诺号源、不保证预约成功、不代办预约；
- 不提供鉴定、估价、交易类信息；
- **不编造**：未查到就写"未查到"，并说明检索限制与官方核实渠道。

**前置**：安装 Node.js ≥ 18（https://nodejs.org/）。

**方式 1（推荐）**：双击 `启动.bat` → 浏览器自动打开 `http://127.0.0.1:8787`

**方式 2（命令行）**：
```bash
node server.mjs          # 或 npm start
```

**访问入口**：

| 入口 | 地址 | 说明 |
|---|---|---|
| 网页版 | `http://127.0.0.1:8787` | 四区布局（条件/结果/依据/提示） |
| **小程序模拟版** | `http://127.0.0.1:8787/mini.html` | 手机壳 + 聊天式交互（模拟小程序形态） |

## 三、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **零依赖静态 HTML/CSS/JS** | 无构建步骤、评审零安装、手机端自适应 |
| 服务端 | **Node.js 原生 HTTP**（本地）/ **Netlify Functions**（云） | 同一份 `lib/` 代码双端复用 |
| 检索 | **博查 + Tavily 双通道并行** | 博查给"来源日期"、Tavily 给"权威命中"，互补 |
| 意图解析 | **规则式**（关键词/正则） | **零幻觉、零成本、可解释、可测试** |
| 输出组装 | **确定性模板**（非大模型生成） | 杜绝"为填满框架而编造"；每条结论必有来源 |
| 会话 | 服务端内存 Map（TTL 7 天） | 满足多轮与隔离；无外部存储依赖 |
| 大模型 | **核心链路不依赖** | 备用 `DEEPSEEK_API_KEY` 已预留，用于后续润色 |

**为什么核心链路不用大模型生成答案**：试题明确"不得通过硬编码或预设冒充动态查询""公开信息不足时如实说明"。**答案由检索结果确定性组装**，每个结论都能点回来源——这比让模型"自由发挥"更符合验收重点。

## 四、检索与信息提取流程

```
用户提问
  → ① 规则式意图解析（城市/科室/资源/职称/急诊/诊疗越界/第N家）
  → ② 条件缺失（如未给城市且属于资源类提问）→ 主动反问，不猜
  → ③ 双通道并行检索（博查 + Tavily），各取 8 条
  → ④ 归一化 + 去重 + **来源权威分级 A/B/C**
  → ⑤ 时效处理：有更新时间则标注；无则写「来源未标注更新时间」（**不用抓取日冒充更新日**）
  → ⑥ 按四段式确定性组装输出
  → ⑦ 会话记忆：记住城市 + 本轮识别出的医院列表（供"第二家的地址呢"承接）
```

**多轮承接示例**（已实测）：
- 第 1 轮「北京有哪些医院设有卒中中心」→ 识别出 5 家医院并存入会话；
- 第 2 轮「**第二家的地址和官方预约入口呢**」→ 正确解析为第 2 家并以其名称重新检索。

## 五、来源核验规则（本方案核心）

**任何一条结论，只能属于以下三态之一；不存在"没有来源的断言"。**

| 三态 | 来源级别 | 展示 |
|---|---|---|
| **A 级 · 可支撑"已核实"** | 政府 / 卫健主管部门 / 医学院校（`*.gov.cn` / `*.edu.cn` / 白名单） | 直接给来源 + 更新时间 |
| **B 级 · 可参考** | 医院官网 / 机构官网（**须在 `lib/hospitals.js` 白名单内，且每条附核实证据 URL**） | 给来源 + 更新时间 |
| **C 级 · ⚠️ 仅线索，待核实** | 聚合站 / 文库 / 百科 / 导医平台 | 明确标注"仅线索，不得作为结论" |

**硬规则**：
1. **来源更新时间 ≠ 本次查询时间**，必须分开标；
2. **未查到 ≠ 没有**——严禁输出"该医院没有 X 科室"；
3. **历史 ≠ 实时**——历史报道/采购公告**不得**表述为"当前可用/有库存"；
4. **不同院区不混用**——地址、科室、排班必须绑定院区；
5. 官网白名单**只增已核实的**，每条必须附证据 URL。

## 六、会话管理

- **会话标识**：前端生成 `sessionId` 并存入 `localStorage`，随每次请求提交；
- **服务端存储**：内存 Map，`TTL = 7 天`、最多 `200` 个会话（FIFO 淘汰）、单会话最多 `100` 轮；
- **多轮记忆**：记住会话内**城市**与**上一轮识别出的医院列表**；
- **会话隔离**：不同 `sessionId` 完全隔离；
- **重置**：页面「重置会话」按钮 / 小程序胶囊里的 ⊙ → 调 `POST /api/reset`。

## 七、异常处理

| 场景 | 行为 |
|---|---|
| 空输入 | 提示示例，不检索 |
| 超长输入（>2000 字） | 提示精简，不检索 |
| 条件缺失（无城市） | **主动反问**，不猜 |
| 检索无结果 | 输出"未查到"三态 + 说明限制 + 给官方核实渠道 |
| 检索服务异常 | 返回 `search_failed`，说明限制并建议官网核实 |
| 诊疗类问题 | 固定拒答话术 + 引导专业医务人员 |
| **紧急求助** | **优先提示拨打 120**，不以继续检索替代求助 |
| 请求体非法/过大 | 返回 `BAD_JSON` / `PAYLOAD_TOO_LARGE` |

**接口约定**（网页版与小程序模拟版共用同一后端）：

```http
POST /api/chat
Content-Type: application/json

{ "message": "北京有哪些医院设有卒中中心", "sessionId": "wx-session-001" }
```

```json
{
  "sessionId": "wx-session-001",
  "status": "ok",
  "answer": "① 查询条件 … ② 查询结果 … ③ 信息依据 … ④ 使用提示 …",
  "sources": [
    { "title": "…", "url": "…", "site": "…", "tier": "A",
      "channels": ["bocha"], "sourceUpdatedAt": "2026-06-23", "queriedAt": "2026-09-23 02:50" }
  ],
  "query": "北京 卒中中心",
  "queriedAt": "2026-09-23 02:50",
  "contextCity": "北京",
  "hospitals": [ { "name": "…", "tier": "A" } ],
  "turn": 2

```

**状态码**：`ok` / `partial` / `need_clarify` / `no_result` / `refused_medical` / `emergency` / `refused_out_of_scope` / `empty` / `too_long` / `search_failed` / `rate_limited` / `error`

**辅助接口**：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/reset` | 重置会话（新会话与旧会话相互隔离） |
| GET | `/api/history?sessionId=` | **查看本会话历史**（城市、识别出的医院、轮次、时间） |
| GET | `/api/stats` | **运行指标**：检索调用次数、缓存命中、重试、失败、缓存大小、限流阈值（**不含任何密钥**） |
| GET | `/api/health` | 健康检查 + 通道配置状态 |
| GET | `/api/sessions` | 会话计数（仅计数与城市，不含对话内容） |

**说明**：本项目未接入在运营的正式小程序（大赛不提供 AppID/账号/生产权限）。`/mini.html` 为**小程序形态的模拟调用方**，用于验证"消息输入 → 会话标识 → 答案与来源返回 → 异常状态"的完整链路。**模拟范围已在此明确标注。**

## 八之二、角色视角（演示用 · 无需登录 · 不采集身份）

赛题**未要求**用户登录或角色；它要求的"身份"只有一个——**会话标识（sessionId）**。
本项目据此确立一条设计原则：**查询对所有人开放；只有"记录类/归属类"功能才需要登录。**

| 视角 | 界面差异 | 是否需要登录 |
|---|---|---|
| **公众 / 患者** | 只显示「查询结果 + 来源 + 使用提示」 | ❌ 不需要 |
| **医护 / 导医** | 增加「**待人工核实来源清单**」：C 级来源 + 原文核对链接 + "来源未标注更新时间"提示 | ❌ 不需要 |
| **管理** | 增加「**运行指标**」面板：真实检索次数 / 缓存命中 / 失败重试 / 活跃会话 / 缓存条目 / 限流阈值 | ❌ 不需要 |

**四条设计理由**：
1. **查询开放**——一上来就要登录，等于把用户挡在门外；查询本身不产生归属数据，无需登录；
2. **登录只挂在"我的××"与"后台"上**——本赛题不含此类功能，故**全程无需登录**；
3. **不采集身份**——赛题明确要求"**不采集患者病历、身份信息等与本赛题无关的敏感数据**"，做成"患者/医护登录"反而**触碰红线**；
4. **三视角共用同一套查询接口**（`POST /api/chat`），差异仅在**附加面板**，**不改变查询结果与来源**。

> ⚠️ 边界说明：该视角切换为**纯前端、演示用**，**不做权限控制、不涉及账号体系**。
> 若未来接入真实小程序并确需角色权限，应在**服务端**用微信登录态（`openid`/`unionid`）校验，**而非前端切换**。

## 九、缓存 / 存储及更新策略

| 存储 | 内容 | 更新策略 |
|---|---|---|
| 服务端内存 Map | 会话（城市、医院列表、轮次计数） | TTL 7 天自动清理；超 200 会话 FIFO 淘汰 |
| **检索结果缓存** | 同一查询的检索结果 | **TTL 10 分钟**、上限 200 条；命中则不消耗检索额度（可用 `/api/stats` 的 `cacheHits` 验证） |
| **限流窗口** | 每会话请求时间戳 | **每会话 20 次/分钟**；超限返回 `rate_limited` |
| 浏览器 `localStorage` | 仅 `sessionId` | 重置会话时更换 |
| **不落库** | 检索原文、页面正文、患者信息 | **不存储**，每次实时检索 |

**「不落库原文」是刻意的**：符合"事实可聚合、原文不搬运、来源给深链"的合规要求，也避免了数据滞留风险。

### 运行保障（进阶3）

| 能力 | 实现 | 验证方式 |
|---|---|---|
| 请求限流 | 每会话 20 次/分钟 | `/api/stats` 的 `rateLimit`；连续请求会出现 `rate_limited` |
| 缓存 | 检索结果 TTL 10 分钟 | `/api/stats` 的 `search.searches` / `search.cacheHits` |
| 失败重试 | 单通道失败自动重试 1 次 | `/api/stats` 的 `search.retries` |
| 调用成本记录 | 累计检索次数 / 缓存命中 / 重试 / 失败 | `/api/stats` |
| 历史查看与清除 | `/api/history` 查看；`/api/reset` 清除 | 见《进阶项实测证据.md》 |
| **降级方式** | 检索失败 → `search_failed` 并建议官网核实；无结果 → `no_result` 且**不断言"没有"**；单通道挂掉另一通道照常出结果 | 测试记录第 5/6 组、《进阶项实测证据.md》 |

## 十、密钥与权限（安全）

- 密钥**只从服务端环境变量或库外文件读取**；
- **不进前端代码、不进公开仓库、不进测试日志、不进截图**；
- `.env.example` 仅含键名不含值；`.gitignore` 已排除 `.env*`（保留 `.env.example`）；
- `/api/health` 只返回"是否配置"，**绝不回显密钥**；
- 检索遵守来源访问规则，**不绕过登录或权限**，不采集与赛题无关的敏感数据。
